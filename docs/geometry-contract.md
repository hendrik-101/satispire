# Synthetic geometry contract

The project targets Satisfactory 1.2. This document's `synthetic-machine-v1` is an independent developer fixture, not old game data. The Vanilla supply layout separately exposes licensed source-local 1.2 machine metadata under `machineGeometry`; see [sources and limits](data/geometry-sources.md). It does not change this synthetic API or its logical units.

`src/domain/geometry.ts` has no production-solver dependency. It exports `syntheticGeometry`, `generateBlock(BlockParameters)` and `generateFloors(FloorsParameters)`, together with their input/output interfaces. Results contain only JSON-compatible values. Identical input produces identical output; caller objects are not mutated.

The document planner (`buildPlanDocument` in `src/planning.ts`) bridges catalog IDs of up to 256 characters to geometry's 128-character ID bound. It preserves ordinary short block and connection IDs; longer or reserved names receive deterministic `generated:block:N` or `generated:connection:N` IDs. All retained short IDs are reserved before assigning generated IDs, preventing collisions with crafted catalog names. Its additive `layoutBindings.blocks` entries map original `itemId` to layout `blockId`; `layoutBindings.connections` entries map layout `connectionId` to original `fromItemId` and `toItemId`. Production identities are preserved. Callers should use these bindings rather than reconstructing a layout ID from an item ID. Generated block IDs are accepted by row commands, including short catalog IDs containing slashes, while reserved keys remain rejected. Geometry's direct ID limits remain unchanged.

The sole supported geometry record is `synthetic-machine-v1`, version 1, with dimensions 4 × 4 × 4 in **logical integer grid units**. Its source is `synthetic`, verification is `synthetic-only`, and generated provenance records `physicalBuildability: "not-verified"`. These numbers are examples for exercising layout contracts. They are not Satisfactory measurements, and these layouts do not establish that anything is buildable in the game. A supplied geometry record must match every field of the supported definition. Unknown IDs, altered dimensions, game-sourced and unverified geometry are rejected. Verified physical game geometry needs a separate reviewed contract and implementation.

## Machine blocks

`generateBlock({count, rows, rotation?, geometry?})` accepts 1–4096 machines, 1–`count` rows, and 0–3 clockwise quarter turns (default 0). In the unrotated coordinate system, x increases eastward and y southward. Input faces west; output faces east. Turns 1, 2, and 3 rotate these to north/south, east/west, and south/north. Rotation transforms machine rectangles, machine port positions, aggregate ports, and topology node positions together. All coordinates remain integral.

Machines fill each row left to right. Rows receive `floor(count/rows)` machines, with one extra in each of the first `count % rows` rows. Thus 16 machines in three rows becomes `[6,5,5]`. Before rotation, the block footprint is `6*ceil(count/rows)+2` wide and `6*rows+2` deep. Each machine begins at `(2+6*column, 2+6*row)`; the synthetic spacing and margin are reserved within the returned block envelope. Odd turns exchange footprint width and depth. `row` and `column` identify the original logical assignment after rotation.

Each machine has a stable local ID and input/output port. The block has one aggregate input and one aggregate output. The manifold graph contains a splitter and a merger per machine: aggregate input → splitter chain → machines → merger chain → aggregate output. All machines are reachable from the input and can reach the output. This is directed **logical topology**, not individual belt routing. Graph edges have no physical path, clearance, throughput, or power interpretation. Port positions and node coordinates are relative to the block origin.

## Stories and lifts

`generateFloors` receives one shared `footprint`, `floorCount`, `floorHeight`, an array of blocks with unique IDs and zero-based `floor` indices, and optional directed connections `{id, fromBlock, toBlock}`. Each block also supplies count, rows, optional rotation/geometry, and an optional integer `position: {x,y}`. Each floor returns the same footprint, an elevation of `index*floorHeight`, placed block envelopes, and reserved corridor rectangles. A placed block's `bounds` is in floor coordinates; its nested block geometry stays in block-local coordinates.

Each connection from one floor to another reserves its own two-unit-wide strip along the east edge, spanning the full footprint depth. Subsequent vertical connections reserve strips immediately to the west. A strip retains identical coordinates on every floor from the lower endpoint through the upper endpoint, including all intermediate floors. It cannot overlap any block envelope on those floors. Floors outside that span are free of that strip. Same-floor connections reserve no lift. The output records `fromFloor`, `toFloor`, and a `liftCorridorId` (null for same-floor connections). Connection direction is from the source block's aggregate output to the destination block's aggregate input. The reservation establishes continuous empty space, not a routed lift or a physical construction guarantee.

Explicit positions are placed and checked first. Remaining blocks are placed in input order by a deterministic first-fit search, scanning candidate y then x coordinates formed from zero and the right/bottom edges of occupied rectangles. Occupied rectangles include lift strips and already placed whole block envelopes. Touching edges are permitted; overlapping interiors and out-of-bounds placements are rejected. The algorithm does not rearrange blocks, choose rows, choose floors, combine lift connections, or optimize packing. An unsuccessful first-fit attempt reports insufficient placement capacity; a different ordering or arrangement may still fit.

## Validation and resource bounds

All counts, dimensions, heights, rotations, indices, and positions must be finite safe integers in their specified ranges. Floor footprints are 1–512 units per dimension; floor count is 1–64; floor height is 4–512. Total height must fit `maxHeight` (default 256, accepted range 1–32768). Each floor respects `maxMachinesPerFloor` (default 4096, accepted range 1–4096). A building permits at most 256 blocks, 16384 machines, and 256 connections. IDs must be unique nonempty strings of at most 128 characters. Connections must reference different existing blocks. Lift strips must fit the footprint.

Invalid geometry, counts, rows, indices, ID references, heights, capacity, overlap, and failed placement throw descriptive `Error` values. Inputs are rejected rather than silently clamped or rounded. These limits concern the synthetic engine and its resource budget; they are not game rules.

Verification lives in `tests/geometry.test.ts`: uneven rows, sixteen-machine arrangements in one through four rows, all four rotations, directed manifold reachability, provenance, identical floor footprints, nonadjacent-floor reservations, same-floor connections, rotated placement, overlap/capacity/height rejection, and deterministic JSON round trips.
